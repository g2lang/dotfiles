# Design rationale

Use only sections that carry a decision or evidence. Keep the record short enough to review alongside the caller examples.

## Problem and constraints

State the intended behavior, approved decisions, source revision, and relevant existing constraints.

## Caller examples

Show realistic usage, returned data, failure handling, and any assumptions a caller must know. Label uncompiled sketches.

## Proposed design

Describe types, operations, ownership, external dependencies, and invariants. Distinguish guarantees encoded in types from conditions that need runtime verification.

## Candidate comparison

Name the candidate artifacts, what each would require callers and maintainers to understand, and the reasons for the recommendation. Record any parts combined and why the resulting design remains consistent.

## Tradeoffs and evidence

Describe costs accepted, experiments performed, and claims that remain unverified. Avoid treating model agreement as evidence of correctness.

## Decisions needed

List unresolved product or architectural choices. State whether the user has approved implementation.

## First implementation increment

Name one useful behavior and the checks that will establish it. Do not start implementation from this document unless authorized.
